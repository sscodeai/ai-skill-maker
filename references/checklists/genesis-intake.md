# Genesis Intake Checklist

Ask enough questions to build a useful day-one maintainer skill. Group questions; do not overwhelm the developer.

## Essential Questions

- What language do you think and review best in?
- Should I use that language for the rest of this interview and bias generated project references toward it? If not, which interview and output languages should I use? Default to English when you have no preference.
- What country or region context should shape the project's public expression?
- Who is the target audience by language and locale?
- What is the product/project trying to become?
- Who is it for, and what should it not try to do?
- What stack do you prefer? Any hard exclusions?
- What language should docs, UI copy, comments, and release notes use?
- What public tone should the project have?
- What quality bar should future AI coding agent sessions enforce before changes are considered done?
- What license, dependency, privacy, security, or hosting constraints matter?
- How should releases happen initially?

## Useful Follow-Ups

- For Japanese projects, should docs use `です・ます`, `だ・である`, or a mixed technical documentation style?
- Should examples, dates, spelling, terminology, or public copy follow a specific country or region?
- What projects, repos, or docs should this feel similar to?
- What maintenance style do you want: stable, experimental, documentation-first, contributor-friendly, performance-focused, or something else?
- What files should future AI coding agents avoid editing without explicit confirmation?
- What are the first three implementation milestones?
- What decisions are intentionally undecided?

## Stop Condition

Proceed when the maintainer skill can answer:

- What to build.
- How to write it.
- How to verify it.
- How to document it.
- How to avoid violating project constraints.
